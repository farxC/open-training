# Roadmap — open-training

## Contexto

O app já atende os requisitos principais do Rafael (log de sessões, splits/programas, corrida, séries-volume por grupo muscular, export/import JSON). Este roadmap organiza a evolução em três horizontes — short-term, medium-term, long-term — e é fundamentado no estado real do código (explorado em 2026-07-23), priorizando reaproveitamento e ordenando itens por dependência: fundações primeiro, features depois.

Decisões incorporadas nesta versão:
- **Mapas/GPS**: adiados para medium/long-term. Curto prazo generaliza modalidades e enriquece métricas (pace, splits, tempo), **sem GPS**, preservando paridade web sem custo extra.
- **Novas modalidades**: ciclismo, natação, calistenia/peso-corporal, mobilidade/alongamento → justifica **generalizar a arquitetura de modalidade** em vez dos checks binários atuais.
- **Recomendações**: movidas para long-term junto da IA. Curto prazo é **puramente descritivo** (métricas melhores, sem camada prescritiva).
- **Exports inteligentes**: filtrados + relatórios formatados (CSV/PDF) + cards compartilháveis.

### Estado atual relevante (baseline confirmado)
- `Modality = "musculacao" | "corrida"` é first-class no schema (`exercises.modality`, `sessions.modality`, `routine_splits.modality`) com discriminador `targetKind: "strength" | "distance"` em `src/data/modalities.ts`. Porém a lista é um array fixo de 2 e há checks binários `=== "corrida"` espalhados (`app/session/new.tsx:609`, `app/session/[id].tsx:145/268/281`, `app/exercises/[id].tsx:71`, `src/hooks/useAnalytics.ts`).
- Corrida **reusa a tabela `sets`** (zera reps/weight, usa `distance_km`/`duration_sec`/`pace_sec`). Não há tabela separada. **Nenhum GPS/localização/mapa** existe.
- Edições de exercício **já propagam** para sessões antigas — nome, grupos musculares e config default são resolvidos por **JOIN em tempo de leitura** (`getSessionExercises` em `src/db/queries.ts:225`), não denormalizados. Config usa `COALESCE(session_exercise_config.*, exercise_config.*)`. **Mas não existe rename nem delete** de exercício (só `createExercise`, `updateExerciseConfig`, `updateExerciseMuscleGroups`).
- Analytics é **100% descritivo** (`useAnalytics.ts`, `src/utils/analyticsAgg.ts`): volume, PRs, streak, frequência e séries-volume com `counting_factor` (0.5/1.0) + média semanal. **Zero recomendações.**
- Export/import existe em `app/settings.tsx` (formato v5, `src/db/importExport.ts` / `importExportApply.ts`), merge aditivo por uuid (`planExerciseMerge`/`planSessionMerge`). `SCHEMA_VERSION = 17`.
- **Sem perfil de usuário.** `user_meta` (key/value) só guarda `schema_version`.
- **Sem theming.** Tema único "warm paper" hardcoded. Paleta de tokens existe em `tailwind.config.js` mas só ~metade adotada; a outra metade é hex inline duplicado em ~40 arquivos. Sem `darkMode`, sem `useColorScheme`. Sem `Button`/`Card` compartilhados (todo botão é `TouchableOpacity` local). `app.json` tem `userInterfaceStyle: "dark"` divergindo da UI clara (bug a corrigir).

## SHORT-TERM

Ordem sugerida: **1 → 3 → 4** (dependem da generalização de modalidade), e **2, 5, 6, 7** em paralelo.

### 1. Generalizar a arquitetura de modalidade *(fundação — habilita 3, 4 e as novas modalidades)*
**Por quê:** hoje modalidade é um enum de 2 com ramificações binárias. Adicionar 4 modalidades exige tornar o sistema orientado a registry + `targetKind`.

- Estender `targetKind` para cobrir os novos modelos: `strength` (musculação, calistenia), `distance` (corrida, ciclismo, natação), **novo** `duration` (mobilidade/alongamento — tempo por posição, sem carga/distância).
- Trocar os checks `modality === "corrida"` por seleção de logger **por `targetKind`** (`app/session/new.tsx`, `app/session/[id].tsx`). Generalizar `RunLogger`/`SetLogger` e adicionar um `DurationLogger` para `targetKind: "duration"`. Calistenia = variação de `strength` (peso corporal / assistido).
- Expandir o registry `MODALITIES` em `src/data/modalities.ts` com ciclismo, natação, calistenia, mobilidade (label, icon, `targetKind`, unidades).
- `sets` já tem colunas suficientes (`distance_km`, `duration_sec`, `pace_sec`, `reps`, `weight_kg`); avaliar flag/campo para peso-corporal e pace-por-100m (natação). Bump de `SCHEMA_VERSION` se colunas novas.
- **Tensão a resolver:** preferência geral por `CHECK` em enums fechados, mas modalidade agora é "crescente". Recomendação: manter validação por registry em TS + `CHECK` só se a lista for tratada como fechada por release. Decidir na execução.

**Arquivos:** `src/data/modalities.ts`, `src/types/exercise.ts` (`Modality`, `ModalityConfig`), `src/db/schema.ts` + `src/db/migrations.ts`, `app/session/new.tsx`, `app/session/[id].tsx`, `src/components/{SetLogger,RunLogger}.tsx` (+ novo `DurationLogger`), `src/hooks/useAnalytics.ts`.

### 2. Edição completa de exercícios (rename + delete) com propagação
**Por quê:** requisito explícito ("edição alterada em todas as sessões"). A propagação **já funciona** para config/grupos via JOIN; falta rename e delete.

- Adicionar `updateExercise` (nome/equipment/type/modality) e `deleteExercise` em `src/db/queries.ts`. Nome é `UNIQUE` — validar colisão.
- Rename propaga automaticamente (JOIN). **Delete:** `session_exercises`/`sets` referenciam `exercise_id` **sem cascade** → escolher entre bloquear delete quando referenciado ou **soft-delete** (flag `is_archived`) para preservar histórico. Recomendação: soft-delete + esconder do picker.
- UI de edição/exclusão na tela de detalhe `app/exercises/[id].tsx`, reusando `ExerciseConfigEditor` e o editor de grupos musculares do `ExercisePickerModal`.

**Arquivos:** `src/db/queries.ts`, `app/exercises/[id].tsx`, `src/components/ExercisePickerModal.tsx`.

### 3. Mais configurações por exercício *(depende de 1)*
**Por quê:** `ExerciseConfig` hoje é rico só para musculação; o editor é **bloqueado** para não-musculação (`app/exercises/[id].tsx:71`).

- Habilitar editor de config para todas as modalidades, com campos por `targetKind` (ex.: corrida → superfície/esteira; natação → tamanho da piscina/estilo; mobilidade → tempo-alvo por posição).
- Estender `ExerciseConfig`/`ExerciseConfigOverride` (`src/types/exercise.ts`) e a tabela `exercise_config`. Bump de `SCHEMA_VERSION` **e** `CURRENT_EXPORT_FORMAT_VERSION` (`src/db/importExport.ts`) — o override por-sessão via `COALESCE` continua funcionando de graça.

**Arquivos:** `src/types/exercise.ts`, `src/db/schema.ts`/`migrations.ts`, `src/components/ExerciseConfigEditor.tsx`, `app/exercises/[id].tsx`, `src/db/importExport.ts`/`importExportApply.ts`.

### 4. Metrificação de volume aprimorada (descritiva) *(depende de 1)*
**Por quê:** métricas devem cobrir as novas modalidades. **Recomendações ficam no long-term.**

- Estender agregações por `targetKind`: volume de distância (corrida/ciclismo/natação), volume de tempo (mobilidade), mantendo séries-volume para strength/calistenia. Reusar `getMuscleSeriesInRange`, `sumRunning`, `sumStrength` e o rollup de média semanal.
- Adicionar visões de analytics por modalidade no filtro existente (`src/components/AnalyticsFilters.tsx`, `useAnalytics.ts`). Nada prescritivo (sem "treine mais X").

**Arquivos:** `src/hooks/useAnalytics.ts`, `src/utils/analyticsAgg.ts`, `src/db/queries.ts`, componentes em `src/components/Analytics*`.

### 5. Perfil do usuário (single-user) *(fundação para medium/long-term)*
**Por quê:** requisito explícito; vira base para preferências (medium) e multi-user (long).

- Nova tabela `user_profile` (ou chaves em `user_meta`): nome, peso corporal, altura, unidades (kg/lb, km/mi), metas. Bump de schema.
- Tela de perfil (novo `app/profile.tsx` ou seção em Settings). Corrigir `userInterfaceStyle: "dark"` divergente em `app.json`.

**Arquivos:** `src/db/schema.ts`/`migrations.ts`, `src/db/queries.ts`, `app/profile.tsx` (novo) ou `app/settings.tsx`, `app.json`.

### 6. Exports inteligentes + imports
**Por quê:** hoje só há backup JSON completo. Requisito: filtrados + relatórios + cards.

- **Filtrados:** parametrizar `buildExportPayload` (`src/db/importExportApply.ts`) por período/modalidade/exercícios.
- **Relatórios formatados:** gerar CSV e PDF legível (resumo de progresso, PRs, volume) — novo `src/db/reportExport.ts`, com fork `.web.tsx` (paridade). PDF via lib compatível com Expo/web (a validar na execução — sempre spikar libs web antes de commitar).
- **Cards compartilháveis:** render de resumo de sessão/PR → imagem (ex.: `react-native-view-shot`) + share; fork web.
- Promover export/import para aba dedicada `app/(tabs)/data.tsx` (4ª tab em `app/(tabs)/_layout.tsx`) ou expandir `app/settings.tsx`. Lógica atual é UI-agnóstica e reutilizável.
- **Nunca** tocar/commitar `scripts/import-history/**` (gitignored, dados privados).

**Arquivos:** `src/db/importExportApply.ts`, `src/db/exportFile.ts`(+`.web`), `src/db/reportExport.ts` (novo), `app/(tabs)/_layout.tsx` + `app/(tabs)/data.tsx` (novo) ou `app/settings.tsx`.

### 7. Usabilidade & UX + fundação de design system *(pré-requisito do medium-term)*
**Por quê:** há linguagem visual coerente mas implementação ad-hoc. Consolidar tokens e criar primitivos é ganho de UX agora e pré-condição para dark mode.

- Criar primitivos compartilhados: `Button` (variantes), `Card`, talvez `ListRow`/`Chip` — substituindo `TouchableOpacity` solto e as receitas de card duplicadas.
- Consolidar os ~40 arquivos com hex inline para os tokens semânticos (`bg-surface`, `text-ink`, etc.) ou um objeto de tema runtime. Sem isso, um toggle de tema depois só afeta metade da UI.
- Passada de UX geral (espaçamento/tipografia tokenizados, estados vazios, feedback de ações).

**Arquivos:** novos em `src/components/ui/`, `tailwind.config.js`, refactor amplo em `src/components/**` e `app/**`.

## MEDIUM-TERM

### 1. Dark / Light themes *(depende de 7)*
- Habilitar `darkMode` no `tailwind.config.js`, definir a paleta dark, aplicar variantes `dark:` (viável só após a consolidação de tokens do item 7).
- Detecção via `useColorScheme` + toggle manual (system/light/dark) persistido em `user_profile`/`user_meta`. Corrigir/consumir `userInterfaceStyle`. Ajustar `global.css` (scrollbar/selection) e os hardcodes de loading em `app/_layout.tsx`.

### 2. Customizações e personalizações de UI
- Preferências do usuário: cor de acento, densidade de layout, quais cards de analytics aparecem, ordem/visibilidade de abas, unidades. Persistidas no perfil/`user_meta` (mecanismo criado no short-term item 5).

## LONG-TERM

Alinhado à direção já registrada em `docs/superpowers/specs/2026-07-14-cloud-sync-backend-architecture-direction.md` (backend Go self-hosted, SQLite embarcado, sync por uuid).

### 1. Backend analítico + sync com banco de dados
- Backend self-hosted para agregações pesadas e persistência remota. **uuids já existem** em exercises/sessions e o export já faz merge por uuid — base pronta para sync.

### 2. Usuários + sync entre dispositivos
- Auth e dados por usuário (evolução do perfil single-user do short-term). Resolução de conflito reaproveitando `planExerciseMerge`/`planSessionMerge` (`src/db/importExport.ts`) já existentes.

### 3. Recomendações de treino com IA
- Camada prescritiva (adiada do short-term): faixas-alvo de volume, sinal de sub/sobre-treino, sugestão de progressão/deload, e recomendações via IA sobre o histórico. Consome as métricas descritivas do short-term item 4.

## Notas transversais (aplicar em todos os itens)
- **Paridade web** é obrigatória: cada feature precisa funcionar no browser (usar forks `*.web.tsx` quando necessário; validar libs no navegador antes de commitar).
- **Versionamento de schema/export**: re-checar `SCHEMA_VERSION` e `CURRENT_EXPORT_FORMAT_VERSION` antes de cada bump — features concorrentes já pularam versões nesta base. Escopar `foreign_key_check` à tabela afetada; gate de rebuild por `hasColumn`, não por `schema_version`.
- **`"order"` é palavra reservada** — sempre citar em SQL/DDL.
- **Offline-first / sem rede** no short e medium-term. Nada de chamadas externas até o backend do long-term.
